# Investigation Analysis: Requirement R1 (Authentication & Session Primary Identifier Migration)

## 1. Executive Summary

This investigation analyzes Requirement R1 of the College Roll Number migration project: migrating primary student authentication, session state management, and identity resolution from internal legacy D-Roll numbers (e.g. D26AB05) to official College Roll Numbers (e.g. 26AB12).

### Key Findings
1. **Root Cause of Identity Mismatch**:
   In `src/data/psgimMasterStudents.ts`, the student dictionary `PSGIM_MASTER_STUDENTS` was populated with naive 1:1 pairs where `collegeRollNo` was created simply by removing the leading 'D' from `dRollNo` (e.g., `D26AB05` -> `26AB05`, `D26AB12` -> `26AB12`). In reality, official College Roll Numbers are assigned alphabetically by student name per cohort. The authoritative mapping (verified against `tests/master_students.cjs` and `google-sheets-addon/all_students.json`) proves:
   - DEVDARSHAN V is internal D-Roll `D26AB05` and official College Roll Number `26AB12`.
   - MATHUMITHA M is internal D-Roll `D26AB12` and official College Roll Number `26AB29`.
   - AKASH VARDHAMAN is internal D-Roll `D26AA01` and official College Roll Number `26AA04`.

2. **Course Registry Duplication Anomaly in `psgimData.ts`**:
   In `src/data/psgimData.ts`, `STUDENT_REGISTRY` contains duplicated records under `"26A..."` keys that were generated by copying the D-Roll records with the same number (`"26AB12"` was copied from `"D26AB12"`, carrying Mathumitha M's courses: MCOB4, ADM3, MC4, SSM2, BS3, EDM1, LA3, SSA1). When querying `getTimetableForStudent('26AB12')`, this resulted in Mathumitha M's classrooms rather than Devdarshan V's classrooms (`LA1 -> LH-101`, `MC3 -> LH-401`, `SSA3 -> LH-101`).

3. **Session Storage Key Architecture**:
   Active session storage in `src/services/storageService.ts` currently uses `@attendance_monitor_auth_user`. Requirement R1 explicitly specifies `@attendance_monitor_roll_no`. A seamless bidirectional fallback and automatic migration mechanism ensures zero session loss for existing users while establishing `@attendance_monitor_roll_no` as the canonical session key storing `26AB12`.

4. **External Legacy Bridging**:
   External servers (PSG Studzone at `ecampus.psgtech.ac.in` and Moodle LMS) require internal D-Roll numbers (`D26AB05`) for API requests. `StudzoneService` and `LmsService` must translate `26AB12` to `D26AB05` under the hood before external network dispatches, keeping all UI displays and local storage purely on `26AB12`.

### The Root Cause Analysis
In the current `src/data/psgimMasterStudents.ts`, line 81 and line 88 are:
```typescript
"D26AB05": { dRollNo: "D26AB05", collegeRollNo: "26AB05", name: "DEVDARSHAN V", batch: "B" },
"D26AB12": { dRollNo: "D26AB12", collegeRollNo: "26AB12", name: "MATHUMITHA M", batch: "B" },
```
Because `collegeRollNo` was erroneously set to `26AB05` instead of `26AB12`:
1. `toNewRollNo("D26AB05")` outputs `26AB05`, NOT `26AB12`.
2. `toOldRollNo("26AB12")` outputs `D26AB12`, resolving to `MATHUMITHA M` instead of `DEVDARSHAN V`.
3. `getMasterStudent("26AB12")` returns `MATHUMITHA M`.

In `tests/master_students.cjs`, the authoritative directory specifies:
```javascript
"D26AB05": { dRollNo: "D26AB05", collegeRollNo: "26AB12", name: "DEVDARSHAN V", batch: "B", dob: "2005-12-13", dobPassword: "13DEC05", bloodGroup: "B +ve" },
"D26AB12": { dRollNo: "D26AB12", collegeRollNo: "26AB29", name: "MATHUMITHA M", batch: "B", dob: "2006-01-26", dobPassword: "26JAN06", bloodGroup: "A +ve" },
```
When `psgimMasterStudents.ts` is populated with this verified master roster:
- `toNewRollNo("D26AB05")` evaluates to `26AB12`.
- `toOldRollNo("26AB12")` evaluates to `D26AB05`.
- `getMasterStudent("26AB12")` evaluates to `DEVDARSHAN V`.
- `getMasterStudent("D26AB05")` evaluates to `DEVDARSHAN V`.

Furthermore, in `src/data/psgimData.ts`, `STUDENT_REGISTRY["26AB12"]` (lines 4731-4744) must match Devdarshan V's courses (`MCOB1, ADM2, MC3, SSM2, BS2, EDM1, LA1, SSA3`), resolving `getTimetableForStudent("26AB12")` to:

Totaling 19 scheduled academic slots.

## 4. Normalization of Legacy D-Roll Inputs

### Normalization Pipeline
When a user enters either `26AB12` or `D26AB05` into `AuthScreen.tsx`:
1. **Sanitization**:
   `cleanRollNo = rollNoInput.trim().toUpperCase().replace(/\s+/g, '')`
2. **Authentication Verification**:
   - For external portal calls (`StudzoneService.verifyLogin`):
     Translate `cleanRollNo` to legacy D-Roll via `toOldRollNo(cleanRollNo)` before sending to external servers. If input is `26AB12`, it sends `D26AB05`.
   - For offline/roster fallback:
     Call `getMasterStudent(cleanRollNo)`.
     Because `getStudentByAnyRoll` checks both `STUDENTS_BY_NEW_ROLL` and `PSGIM_MASTER_STUDENTS`, both `26AB12` and `D26AB05` resolve directly to Devdarshan V.
     Compare `student.dobPassword.toUpperCase() === rawPassword.toUpperCase()`.
3. **Identifier Normalization**:
   `officialRoll = toNewRollNo(cleanRollNo)`
   - If input was `D26AB05` -> normalizes to `26AB12`.
   - If input was `26AB12` -> normalizes to `26AB12`.
4. **Credential Persistence Normalization**:
   Pass `officialRoll` into `StudzoneService.saveCredentials`:
   ```typescript
   await StudzoneService.saveCredentials({
     rollNo: officialRoll,
     dobPassword: rawPassword,
     remember: rememberMe,
   });
   ```
   This guarantees that subsequent app loads pre-populate with `26AB12`.
5. **Session Initiation**:
   Invoke `onLoginSuccess(officialRoll)` passing `26AB12`.

## 5. Session Storage Key Architecture & Continuity

### Canonical Key vs Legacy Key
Requirement R1 requires that:
"The active session roll number stored in memory and local storage (@attendance_monitor_roll_no) is the College Roll Number (26AB12)."

`StorageService` must support:
- `SESSION_ROLL_NO: '@attendance_monitor_roll_no'` (Canonical)
- `AUTH_USER: '@attendance_monitor_auth_user'` (Legacy compatibility)

### Storage Migration Protocol in `StorageService`
```typescript
const STORAGE_KEYS = {
  SESSION_ROLL_NO: '@attendance_monitor_roll_no',
  AUTH_USER: '@attendance_monitor_auth_user',
  // ... other keys
};

async getAuthUser(): Promise<string | null> {
  try {
    // 1. Try canonical key
    let rollNo = await AsyncStorage.getItem(STORAGE_KEYS.SESSION_ROLL_NO);
    if (!rollNo) {
      // 2. Fall back to legacy key
      rollNo = await AsyncStorage.getItem(STORAGE_KEYS.AUTH_USER);
    }
    if (rollNo) {
      // 3. Normalize to College Roll Number
      const officialRoll = toNewRollNo(rollNo);
      if (officialRoll !== rollNo || !(await AsyncStorage.getItem(STORAGE_KEYS.SESSION_ROLL_NO))) {
        await AsyncStorage.setItem(STORAGE_KEYS.SESSION_ROLL_NO, officialRoll);
      }
      return officialRoll;
    }
    return null;
  } catch {
    return null;
  }
},

async setAuthUser(rollNo: string): Promise<void> {
  try {
    const officialRoll = toNewRollNo(rollNo);
    await AsyncStorage.setItem(STORAGE_KEYS.SESSION_ROLL_NO, officialRoll);
    await AsyncStorage.setItem(STORAGE_KEYS.AUTH_USER, officialRoll);
  } catch (e) {
    console.warn('Storage error:', e);
  }
},

async clearAuthUser(): Promise<void> {
  try {
    await AsyncStorage.removeItem(STORAGE_KEYS.SESSION_ROLL_NO);
    await AsyncStorage.removeItem(STORAGE_KEYS.AUTH_USER);
  } catch (e) {
    console.warn('Storage error:', e);
  }
}
```

### Attendance Records & Period Reminders Continuity
Existing records previously saved under `D26AB05` must not be lost when the user is migrated to `26AB12`.
In `StorageService.getPeriodRecords(rollNo)`:
```typescript
async getPeriodRecords(rollNo: string): Promise<Record<string, PeriodAttendanceRecord>> {
  try {
    if (!rollNo) return {};
    const officialRoll = toNewRollNo(rollNo);
    const oldRoll = toOldRollNo(rollNo);
    const key = `${STORAGE_KEYS.PERIOD_RECORDS}${officialRoll.toUpperCase()}`;
    const data = await AsyncStorage.getItem(key);
    if (data) return JSON.parse(data);

    // Backward compatibility: check under legacy D-Roll key
    if (oldRoll !== officialRoll) {
      const legacyKey = `${STORAGE_KEYS.PERIOD_RECORDS}${oldRoll.toUpperCase()}`;
      const legacyData = await AsyncStorage.getItem(legacyKey);
      if (legacyData) {
        // Migrate to new canonical key
        await AsyncStorage.setItem(key, legacyData);
        return JSON.parse(legacyData);
      }
    }
    return {};
  } catch (e) {
    console.warn('Error reading period records:', e);
    return {};
  }
}
```
The identical fallback pattern applies to `getPeriodReminders` and `getSurplusAlerts`.

## 7. Potential Edge Cases & Regressions

1. **Case Sensitivity & Whitespace**:
   Inputs such as `26ab12`, ` 26AB12 `, `d26ab05` are sanitized using `.trim().toUpperCase().replace(/\s+/g, '')`.
2. **External Studzone Scraper Compatibility**:
   If the student logs in with `26AB12`, background requests to `ecampus.psgtech.ac.in` will fail with "Invalid Roll No" unless bridged to `D26AB05`. Translating via `toOldRollNo(rollNo)` in `studzoneService.ts` ensures uninterrupted live attendance syncing.
3. **Moodle Portal Sync**:
   `LmsService.resolveMoodleUsername` already uses `toOldRollNo(rollNo)` to obtain `D26AB05`. However, UI displays in `ReconcileScreen.tsx` must show `26AB12` rather than displaying the resolved Moodle username.
4. **App Cold Startup with Existing Saved Session**:
   Users who previously logged in under `D26AB05` will have `savedRollNo = "D26AB05"`. `initSession()` in `App.tsx` must normalize this to `26AB12`, update `@attendance_monitor_roll_no`, and initialize all screens with `26AB12`.
5. **Zero Emoji Policy**:
   All touched code and error messages must contain strictly zero emojis.
